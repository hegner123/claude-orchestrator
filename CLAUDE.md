## Repository Purpose

This is an **AI-powered component build system** for Umbraco CMS projects. The system uses multi-agent workflows to generate full-stack components from design images with minimal operator intervention. Documentation provides context for building a system that transforms visual designs into:
- Backend schemas (UDA files)
- API converters (C# ApiSafeConverters)
- TypeScript type definitions
- React components with styling

## Architecture Overview

### Three-Layer Data Flow

The system operates on a strict three-layer architecture that **must remain synchronized**:

```
LAYER 1: SCHEMA (UDA Files)
├─ Location: src/UmbracoProject/umbraco/Deploy/Revision/
├─ Purpose: Define WHAT fields exist and HOW they're configured
└─ Role: Source of truth for content structure

       ↓ Bound by EditorAlias

LAYER 2: TRANSFORMATION (ApiSafeConverters)
├─ Location: src/Seed.Core/ApiSafeConverters/ (generic)
│            src/Seed.Backoffice.Extensions/ApiSafeConverters/ (project-specific)
├─ Purpose: HOW data transforms at runtime (Umbraco objects → JSON)
└─ 80% automatic passthrough, 20% custom converters

       ↓ JSON Serialization

LAYER 3: CONSUMPTION (TypeScript Types)
├─ Location: src/Seed.Web/lib/umbraco/types/
├─ Purpose: WHAT shape the data has on the frontend
└─ Role: Type-safe frontend consumption
```

**CRITICAL COMPLETION CRITERIA**: Any change affecting data types requires:
1. ✅ UDA file created/modified with valid JSON
2. ✅ Converter requirement satisfied (existing/custom/automatic)
3. ✅ Property added to document type (if applicable)
4. ✅ TypeScript types updated in ALL consuming components
5. ✅ TypeScript compilation succeeds: `npx tsc --noEmit` (zero errors)

### Project Classification

```
PROJECT                      TYPE          ROLE                    WHEN TO USE
================================================================================
Seed.Core                    Library       Infrastructure          Generic/reusable services, base converters
Seed.DataTypes               Library       Property Editors        Reusable backoffice controls
Seed.Backoffice.Extensions   Library       Business Logic          Project-specific converters, features
UmbracoProject               Host App      Runtime Container       Schema (UDA files), configuration
Seed.Web                     Frontend      UI/Presentation         React components, TypeScript types
```

**Decision Tree for "Where Does This Work Belong?"**:

- Backoffice UI control (property editor)?
  - Reusable across industries → `Seed.DataTypes/{EditorName}/`
  - Project-specific → `Seed.Backoffice.Extensions/CustomPickers/`
- Data transformation for API?
  - Standard Umbraco types → `Seed.Core/ApiSafeConverters/`
  - Custom document types → `Seed.Backoffice.Extensions/ApiSafeConverters/`
- Schema definition → `UmbracoProject/umbraco/Deploy/Revision/*.uda`
- Frontend component → `Seed.Web/common/components/`
- TypeScript types → `Seed.Web/lib/umbraco/types/`
- Business logic → `Seed.Backoffice.Extensions/`
- Configuration → `UmbracoProject/Program.cs` or `appsettings*.json`

## Critical Patterns

### Converter Decision Matrix

**80% of properties use automatic passthrough** (no converter needed):
- `Umbraco.TextBox`, `TextArea` → `string`
- `Umbraco.Integer`, `Decimal`, `Slider` → `number`
- `Umbraco.TrueFalse` → `boolean`
- `Umbraco.DateTime` → `string` (ISO 8601)
- `Umbraco.DropDown.Flexible` → `string` or union type
- `Umbraco.CheckBoxList` → `string[]`

**20% require custom converters**:
- `Umbraco.MediaPicker3` → `MediaApiSafeConverter` → `ImageModel`
- `Umbraco.ContentPicker` → `PublishedContentApiSafeConverter` → `UmbracoNode`
- `Umbraco.BlockGrid` → `BlockGridApiSafeConverter` → `BlockGridItem[]`
- `Umbraco.BlockList` → `BlockListApiSafeConverter` → `BlockListItem[]`
- Custom document types → Project-specific converters

### Naming Conventions

**Data Types** (context-specific to prevent accidental reuse):
- Format: `{Component/Feature} - {Property Name} - {Editor Type}`
- Example: `"Headline - Full Background Image - Image - Media Picker"`
- Example: `"Team - Athlete - Image - Media Picker"`

**File Patterns**:
- ApiSafeConverter: `{Name}ApiSafeConverter.cs`
- UDA Data Type: `data-type__{uuid-with-dashes}.uda`
- UDA Document Type: `document-type__{uuid-with-dashes}.uda`
- TypeScript Type: `{name}.type.ts`
- React Component: `{ComponentName}.tsx` (PascalCase)

### UDA File Management

**NEVER manually edit UDA files** - they are auto-generated by the Umbraco backoffice. UDA files in `src/UmbracoProject/umbraco/Deploy/Revision/` are the source of truth for schema but should only be modified through the backoffice UI.

**UUID Generation**:
- Generate: `uuidgen` (macOS/Linux)
- Format: `XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX`
- With dashes: Filename, property Keys
- Without dashes: UDI values (e.g., `umb://data-type/{uuid-no-dashes}`)

## AI Component Build Workflow

The system implements a **5-phase workflow** for generating components from design images:

### Phase 0: Input Collection
- Design images (desktop/mobile)
- Property list (if available)
- Description text
- Design tokens (if available)

### Phase 1: Vision Analysis (Automated)
Vision agent:
- Extracts semantic structure
- Identifies UI patterns and interactions
- Matches to existing component patterns
- Generates **Component Contract** with confidence scores
- Extracts design tokens

### Phase 2: Operator Confirmation (Selective)
Present for review:
- Low-confidence decisions only (< 0.75 confidence)
- Ambiguous functionality (modal vs navigation)
- Novel patterns (not in library)

### Phase 3: Parallel Agent Execution (Automated)
Orchestrator spawns agents with Component Contract:
- **Agent 1: Backend Structure** - Create/reuse datatypes, verify/create converters, update document type UDA
- **Agent 2: TypeScript Definitions** - Generate type definitions, update master routing, create interface files
- **Agent 3: Component Scaffold** - Generate component file from template, map props, add interaction handlers
- **Agent 4: Styling** - Generate CSS/SCSS from design tokens, apply responsive breakpoints

### Phase 4: Validation Gates (Automated + Selective)
- **Gate 1: Structural** (must pass) - TypeScript compiles, component renders, all fields mapped
- **Gate 2: Layout** (threshold-based) - Screenshot similarity > 70%, responsive breakpoints
- **Gate 3: Visual** (iterative, max 3 cycles) - Style agent refines until > 85% similarity
- **Gate 4: Functional** (automated) - Interactions work, accessibility passes

### Phase 5: Delivery
- Commit all files
- Generate documentation
- Add to component library
- Store operator corrections for learning

## Component Contract Schema

The **Component Contract** is the central artifact that maintains context across all agents:

```typescript
interface ComponentContract {
  version: string;
  componentId: string;
  metadata: {
    created: string;
    lastModified: string;
    operatorApproved: boolean;
    confidenceScore: number;
  };
  contentType: ContentTypeDefinition;      // Backend schema
  visualStructure: VisualStructureDefinition;  // Layout/regions
  derivedFunctionality: FunctionalityDefinition;  // Interactions
  dependencies: DependenciesDefinition;    // Converters, child types
  validationResults: ValidationResults;
}
```

**Key Features**:
- Single source of truth for all agents
- Explicit field mapping persists across context windows
- Validation checkpoints verify against contract
- Confidence scores enable selective operator intervention

## Success Metrics

Target metrics for automation improvement:
1. **Operator Intervention Rate**: < 3 decisions per component
2. **First-Pass Success Rate**: > 60% pass Gate 2 without operator review
3. **Pattern Recognition Accuracy**: > 85% correct pattern matching
4. **Style Convergence Speed**: < 3 iterations to 85% visual similarity
5. **End-to-End Time**: < 5 minutes operator time for familiar patterns
